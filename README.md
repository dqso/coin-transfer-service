# Coin Transfer Service

Сервис переводов монет между аккаунтами игроков. Условие задания — в [TASK.md](TASK.md).

## Запуск

```sh
cp .env.example .env   # задать свои значения
docker compose up --build
```

Поднимаются:

| Сервис     | Что делает                                               | Адрес                              |
|------------|----------------------------------------------------------|------------------------------------|
| `postgres` | PostgreSQL 18                                            | `localhost:5432`                   |
| `migrate`  | Применяет миграции из `migrations/` (tern) и завершается | —                                  |
| `app`      | Две реплики сервиса, стартуют после миграций             | `localhost:3000`, `localhost:3001` |

После миграций в базе есть аккаунты `acc_1` … `acc_10` по 1000 монет.

Локально без Docker (нужен PostgreSQL с применёнными миграциями):

```sh
set -a && . ./.env && set +a
PGHOST=localhost go run ./app/cmd/main.go
```

## Эндпоинты

| Метод  | Путь                                  | Описание                    |
|--------|---------------------------------------|-----------------------------|
| `POST` | `/api/v1/transfers`                   | Создать перевод             |
| `GET`  | `/api/v1/transfers/{idempotency_key}` | Получить перевод            |
| `GET`  | `/api/v1/accounts/{id}`               | Получить аккаунт с балансом |
| `GET`  | `/livez`                              | Liveness probe              |
| `GET`  | `/readyz`                             | Readiness probe             |
| `GET`  | `/docs`                               | Swagger UI                  |
| `GET`  | `/openapi.yaml`                       | OpenAPI-спецификация        |

Спецификация лежит в [`app/internal/transport/http/openapi.yaml`](app/internal/transport/http/openapi.yaml), HTTP-слой генерируется из неё через [ogen](https://github.com/ogen-go/ogen).

### Коды ответов

Сверх контракта из ТЗ в ответы с ошибкой и в отказы добавлено числовое поле `code`. Первые три цифры — HTTP-статус, последние три — номер внутри статуса:

```json
{ "code": 409001, "message": "idempotency key is already used with other payment details" }
```

| Код      | Когда                                                     |
|----------|-----------------------------------------------------------|
| `400001` | Невалидный запрос: пустой ключ или аккаунт, `amount <= 0` |
| `404001` | Перевод не найден                                         |
| `404002` | Аккаунт не найден                                         |
| `409001` | Ключ идемпотентности уже использован с другими данными    |
| `409002` | Перевод с этим ключом ещё выполняется                     |
| `422001` | Отказ: перевод самому себе                                |
| `422002` | Отказ: аккаунт не найден                                  |
| `422003` | Отказ: недостаточно средств                               |
| `500001` | Внутренняя ошибка                                         |

Отказы (`422xxx`) — это результат перевода: они сохраняются, и повтор с тем же ключом вернёт тот же отказ. `GET /api/v1/transfers/{idempotency_key}` для отклонённого перевода тоже возвращает `reason` и `code`.

## Тесты

```sh
make help                      # список команд
make generate                  # перегенерировать код из openapi.yaml
make test                      # unit-тесты
make test-integration          # интеграционные тесты
make test-integration-verbose  # то же по одному тесту, с логами запросов и ответов
```

Интеграционные тесты (`app/tests/integration/`, build tag `integration`) поднимают PostgreSQL в testcontainers, применяют миграции проекта в шаблонную базу и для каждого теста создают её копию. Проверяются сценарии из ТЗ, идемпотентность, конкурентные переводы и зависшие переводы. После каждого теста сверяется бухгалтерия: сумма балансов не меняется, у каждого перевода сходятся проводки.

## Что дальше

### Для продакшена

- **Срок жизни ключей идемпотентности — 24 часа:** отдельная таблица ключей и фоновая очистка пачками.
- **История операций аккаунта:** `GET /api/v1/accounts/{id}/postings` с пагинацией по курсору.
- **Метрики Prometheus:** RPS и латентность, переводы по статусам и кодам отказа, число зависших переводов, пул pgx.
- **UUID вместо числового `transfer_id` в API,** чтобы по своим переводам нельзя было оценить их общее число в системе.
- **Скрыть служебный аккаунт treasury** из API и запретить переводы с него и на него.

### Почему такой стек

- **PostgreSQL** — работа с финансовыми данными: ACID-транзакции и блокировки строк (`FOR UPDATE`, `SKIP LOCKED`) дают атомарное изменение балансов и проводок без распределённых локов.
- **pgx** — текущий стандарт для PostgreSQL в Go: явный SQL, полный контроль над запросами и блокировками, быстрый драйвер. **tern** — миграции на чистом SQL от авторов pgx, сложные миграции не требовались.
- **ogen** — сервер генерируется из `openapi.yaml`: контракт — единый источник правды, валидация из коробки, без рефлексии. Привычнее swaggo, но он устарел.
- **testify** сокращает тесты и упрощает их чтение, **gomock** генерирует моки, чтобы тестировать слои по отдельности.

### Инфраструктура и масштабирование

Деплой в Kubernetes: Deployment с HPA, probes `/livez` и `/readyz` уже есть, миграции — отдельный Job перед релизом. Сервис stateless, все гарантии держит база, поэтому реплик может быть сколько угодно. Если в переводе появятся другие шаги (вызовы других сервисов, сложные расчёты), стоит перейти на saga и inbox.

### Компромиссы

Пункты из раздела «Для продакшена» сознательно не сделаны, чтобы сосредоточиться на ядре задания — корректности переводов, идемпотентности и конкурентности:

- ключи идемпотентности хранятся бессрочно — так `GET` по ключу остаётся простым поиском по уникальному индексу;
- нет истории операций аккаунта и метрик — проводки уже пишутся, эндпоинт и `/metrics` добавляются без изменения логики переводов;
- в API отдаётся числовой `transfer_id` вместо UUID;
- служебный аккаунт treasury виден через API.
